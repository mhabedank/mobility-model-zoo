## (b) AUTOSAR IDS: IdsM, IdsR, SEM, security sensors, QSEv

Documents read (all downloaded from autosar.org):
- *Requirements on Intrusion Detection System*, AUTOSAR FO R25-11, **Document ID 976** [V] — https://www.autosar.org/fileadmin/standards/R25-11/FO/AUTOSAR_FO_RS_IntrusionDetectionSystem.pdf
- *Specification of Intrusion Detection System Protocol*, AUTOSAR FO R25-11, **Document ID 981** [V] — https://www.autosar.org/fileadmin/standards/R25-11/FO/AUTOSAR_FO_PRS_IntrusionDetectionSystem.pdf
- *SWS Intrusion Detection System Manager* (Classic Platform), R24-11, **Document ID 977** [V] — https://autosar.org/fileadmin/standards/R24-11/CP/AUTOSAR_CP_SWS_IntrusionDetectionSystemManager.pdf (an Adaptive Platform SWS also exists [U])

What the standard specifies:
1. **Architecture** [V]: "An onboard IDS according to the AUTOSAR standard consists of ... Security Sensors, Intrusion Detection System Manager (IdsM), Security Event Memory (Sem), Intrusion Detection System Reporter (IdsR)". It is explicitly a *distributed* onboard IDS.
2. **Security sensors and security events (SEv)** [V]: "AUTOSAR BSW modules, CDD and SWC can act as Security Sensors." AUTOSAR "standardizes a subset of Security Event Types which can be reported by the AUTOSAR BSW". SWCs and CDDs "can also report custom Security Event Types which are not standardized". Sensor properties are exchanged in the **Security Extract (SecXT)** format.
   - The standardised CAN-related events are low level. CanIf R24-11 has `SEV_CAN_ERRORSTATE_BUSOFF`, `SEV_CAN_ERRORSTATE_PASSIVE`, `SEV_CAN_RX_ERROR_DETECTED`, `SEV_CAN_TX_ERROR_DETECTED`; SecOC has `SEV_SECOC_MAC_VERIFICATION_FAILED` and `SEV_SECOC_FRESHNESS_NOT_AVAILABLE` [V, grep of the SWS PDFs]. Nothing in the standard detects timing or payload anomalies.
3. **IdsM** [V]: "The IdsM buffers the reported security events. Furthermore the IdsM applies a set of consecutive filters to the reported SEv. A set of consecutive filters is called a Filter Chain. If SEv pass their Filter Chain they are regarded as Qualified Security Events (QSEv)." The QSEv is then persisted in the Sem and/or serialised and sent to the IdsR.
   - The CP SWS filter chain [V] contains:
     - blocker filters (Reporting Mode Filter, Block State Filter, machine/BswM state)
     - sampling filters ("forward every Nth")
     - aggregation filters (Event Aggregation, Event Threshold)
     - rate-limitation filters (Event Rate Limitation, Traffic Limitation)
   - Sensor APIs [V]: `IdsM_SetSecurityEvent`, `...WithContextData`, `...WithCount`, `...WithTimestampCount...`. An optional context-data modifier callout also exists.
   - RS requirement [RS_Ids_00511] [V]: "IdsM shall support limiting the rate of QSEvs transmitted to the IdsR and the bandwidth consumed by these transmissions", with the rationale "Limit network bus load caused by IDS". Further requirements cover timestamps (RS_Ids_00502/00503), optional QSEv authentication/signature, and configurable I-PDU for QSEv propagation.
   - Design assumptions in the SWS [V]: "It is acceptable that SEvs are dropped depending on their reporting frequency and criticality". Security events "can occur during the normal operation without any attack happening".
4. **Sem** [V]: "A user defined diagnostic event memory which is independent" of the Dem primary memory. In CP it is implemented through Dem as a "Dem / Sem sink"; there is an `IdsM_DemReadQSEv` API.
5. **IdsM to IdsR protocol (PRS, doc 981)** [V]: it defines "the format, message sequences and semantics" for transmitting QSEv from IdsM to IdsR.
   - It covers protocol header, IdsM instance ID and sensor instance ID, AUTOSAR or OEM timestamp, context data (with version and long/short size), a signature as an authentication option (new in R25-11), and PDU type.
   - "push-interface" only; a pull interface "is not covered".
   - "designed to work for all bus system. The software stack must be able to send and receive I-PDUs" (CAN, UDP, TCP depending on the network).
   - "The elements of the IDS protocol can be mapped to the syslog format by the IdsR".
   - Recommended maximum of 16 kByte per QSEv.
6. **IdsR is not specified** [V]: "A specification of the IdsR is not provided by AUTOSAR." It "should typically further enrich the received data e.g. with geo-position" and may forward to a SOC/SIEM.
7. **Detection logic is not standardised.** AUTOSAR standardises the plumbing: event types, the event-handling API, filter chains, rate limiting, storage and the transport format. It does not standardise how a sensor decides that CAN traffic is malicious. This follows from the documents above (sensors are BSW/CDD/SWC, custom event types are allowed, the IdsR is out of scope) [V, inference from the text]. Vector's 2020 article says the same thing in other words: OEMs define requirements, BSW vendors implement IdsM/IdsR, and "security experts" contribute "advanced security sensors, e.g., sensors based on artificial intelligence (AI)" [V].
8. History: Vector says the IdsM was introduced with AUTOSAR 4.4 and that security-event standardisation was reworked for R20-11 [V, 2020 article]. Basic IdsM specs have been in every CP and AP release since R20-11 [U].

## (c) Regulatory and standards drivers

### UNECE R155 (CSMS and vehicle-type approval)
Source: UN R155, E/ECE/TRANS/505/Rev.3/Add.154, 4 March 2021 (Wayback copy of the UNECE PDF) [V] — https://web.archive.org/web/2022/https://unece.org/sites/default/files/2021-03/R155e.pdf

- **7.2.2.2 (g)** [V]: the CSMS shall include "The processes used to monitor for, detect and respond to cyber-attacks, cyber threats and vulnerabilities on vehicle types". Item (h) adds "processes used to provide relevant data to support analysis of attempted or successful cyber-attacks".
- **7.2.2.4** [V]: monitoring "shall be continual". It shall "(a) Include vehicles after first registration" and "(b) Include the capability to analyse and detect cyber threats, vulnerabilities and cyber-attacks from vehicle data and vehicle logs". This capability must respect privacy and consent.
- **7.3.7** [V]: "The vehicle manufacturer shall implement measures for the vehicle type to: (a) Detect and prevent cyber-attacks against vehicles of the vehicle type; (b) Support the monitoring capability of the vehicle manufacturer ...; (c) Provide data forensic capability".
- **7.4.1** [V]: report monitoring results to the approval authority "at least once a year".
- **Annex 5, Part B** [V]: threat 11.1 "Malicious internal (e.g. CAN) messages" maps to mitigation **M15**, "Measures to detect malicious internal messages or activity should be considered". DoS threats (8.1, 8.2, 24.1) map to **M13**, "Measures to detect and recover from a denial of service attack".
- **7.3.4** [V]: Annex 5 mitigations must be implemented where "relevant for the risks identified", but "if a mitigation referred to in Annex 5 ... is not relevant or not sufficient ... another appropriate mitigation" may be used.
- **Conclusion**: R155 does **not** literally require an in-vehicle IDS. It requires processes for monitoring, detection and response (7.2.2.2 g), vehicle-type measures to detect and prevent attacks and to support monitoring and forensics (7.3.7), and M15 says detection of malicious CAN messages "should be considered". In practice this pushes OEMs towards onboard security sensors plus logging and reporting (AUTOSAR IdsM/IdsR) feeding a backend VSOC. The R155 text does not specify the detection technology. Whether a type-approval authority would accept an approach without onboard detection is an interpretation question; the TFCS interpretation document on 7.3.7 exists but I did not open it [U] (https://globalautoregs.com/documents/22535).

### ISO/SAE 21434:2021
Paywalled; I could not open the standard. Everything here is [U], from training-course and secondary descriptions:
- Clause 8 "Continual cybersecurity activities" has four parts: cybersecurity monitoring (8.3), cybersecurity event evaluation (8.4), vulnerability analysis (8.5) and vulnerability management (8.6).
- Its work products are WP-08-01 to WP-08-06 (monitoring sources, triggers, cybersecurity events, weaknesses, vulnerability analysis, evidence of managed vulnerabilities). Clause 13 (operations and maintenance) covers incident response.
- It is a process standard. It names internal and external information sources for monitoring but does not prescribe an IDS or any detection technique. A secondary academic summary notes that it "lacks on in-vehicle monitoring" [U].
- Sources: https://ul.com/sis/training/introduction-isosae-21434 ; https://www.tuev-nord.de/fileadmin/Sites/TUEV_NORD/Dienstleistungen/Certification/Files/PDFs_IT/Whitepaper/Whitepaper-ISO-SAE-21434-EN.pdf

### China GB 44495-2024 (Technical requirements for vehicle cybersecurity)
- Issued 23 August 2024 by SAMR/SAC; mandatory from 1 January 2026; applies to M, N and O vehicles with at least one ECU [U, multiple snippets including TÜV SÜD].
- A sample page from chinesestandard.net shows CSMS clause 6.7 [V, partial translation]: "Ability to identify vehicle cyber-attacks; Monitoring and data forensics capabilities for vehicle-related cyber-attacks, cyber threats and vulnerabilities." It also shows 7.1.2.3, a security log for remote-control commands [V]. https://www.chinesestandard.net/PDF_MS.aspx/GB44495-2024
- The vehicle-level technical requirements were seen only in a Chinese secondary interpretation (cnzev.com), not in the standard. They are numbered 7.2.10–7.2.12 per search snippet [U]:
  - "车辆应具备识别车辆通信通道遭受拒绝服务攻击的能力，并对攻击进行相应的处理" ("the vehicle shall be able to identify DoS attacks on its communication channels and handle them"). The interpretation lists CAN bus and in-vehicle Ethernet among the channels tested and suggests "IDSP + CAN-ID filtering" [V for the interpretation text].
  - "车辆应具备识别恶意的 V2X 数据、恶意的诊断数据能力" ("identify malicious V2X data and malicious diagnostic data") [V interpretation].
  - A communication-channel security-event log with retention of "不少于 6 个月" ("at least 6 months") [V interpretation].
  - Source: https://www.cnzev.com/6223.html
- **Conclusion**: GB 44495 is more specific than R155. It contains testable vehicle-level requirements to *identify DoS on communication channels (including CAN)* and *malicious diagnostic data*, and to keep security logs. It still does not mandate a general-purpose CAN anomaly IDS. Rate and ID filtering plus logging can satisfy the DoS item according to the interpretation above. Exact wording should be checked against the official text (openstd.samr.gov.cn), which I did not open.

## (d) Observations for an open-source competitor

1. **Host-side commercial CAN IDS is mostly rule- or specification-based.**
   - ETAS states "heuristic and signature-based" detection with automatic rule generation, plus comparison against expected behaviour [V].
   - AUTOCRYPT generates policies from the DBC [V]. Cymotive uses "configurable rules and algorithms" [V]. Karamba is deterministic [V]. The NXP TJA115x uses fixed per-ID pass/block lists and flooding thresholds [V].
   - ML on the vehicle is claimed only by VicOne (ML layered on 2,000+ rules, mainly to cut false positives) and by Argus in 2016 ("heuristic and learning algorithms").
   - A DBC-driven spec/rule engine is therefore the baseline to match; ML should be offered as an optional extra layer, not a replacement.
2. **ML lives mostly in the cloud VSOC.** Upstream (digital twins, agentless, AI), VicOne xNexus, ETAS CycurGUARD ("big data") and Cymotive IEP all do the heavy analytics offboard. The in-vehicle part is the sensor, the filter and the reporter.
3. **Nobody publishes reproducible benchmarks.** The only figures found are:
   - Arilou "100% detection ... zero false positives" (UMTRI, 2019, no protocol)
   - Karamba "zero false positives", "<1% CPU", "<1MB"
   - AUTOCRYPT "extremely low false detection rate"
   - No vendor publishes a dataset, an attack set, or detection-rate and false-positive curves. A public benchmark on open datasets (for example ROAD, HCRL), with published per-attack detection rate, FPR and latency, would be a real differentiator.
4. **Footprint is almost never disclosed.** Karamba's "<1 MB / <1% CPU" (host CFI, not CAN) is the only public number. Publishing exact flash/RAM/cycles-per-frame figures on a reference MCU (for example a Cortex-M4/M7 or S32K) would be unusual and credible.
5. **AUTOSAR gives an open-source IDS an integration slot.** AUTOSAR standardises the event plumbing but leaves detection logic open [V].
   - A competitor can be a "security sensor" that reports via `IdsM_SetSecurityEvent*`, uses the PRS IDS QSEv format (doc 981), and uses custom event types declared in SecXT.
   - This plugs into Vector, ETAS or EB stacks without replacing them. The IdsR is unspecified [V], which leaves room for an open IdsR or syslog bridge.
6. **The regulatory pull is for monitoring, not for any particular algorithm.**
   - R155 requires processes and vehicle measures to detect and support monitoring and forensics (7.2.2.2 g, 7.2.2.4, 7.3.7). M15 only says CAN-message detection "should be considered" [V].
   - GB 44495 is more concrete: identify DoS on channels including CAN, identify malicious diagnostic data, keep logs for at least 6 months [V via interpretation; clause numbers U].
   - An open-source tool should map its outputs to these clauses (an evidence pack for type approval) rather than claim to be "R155-compliant IDS".
7. **Hardware offload and the physical layer are moving targets.** The NXP S32G LLCE runs IDPS rules [V], and TJA115x transceivers enforce ID and flood rules in silicon [V]. A software IDS should treat these as upstream filters, not compete with them.
   - Its value is cross-ID timing, sequence and payload semantics that per-node transceivers cannot see.
8. **The market is consolidating and fragile.** Argus went to Continental/EB and was renamed PlaxidityX [V]; Cybellum went to LG [U]; VicOne is part of Trend Micro [V]; Cymotive is linked to VW [U]; GuardKnox went insolvent in January 2025 [V]. Several vendors (Karamba, C2A, Cybellum, Irdeto) are not CAN-IDS vendors at all. The number of vendors with an actual in-vehicle CAN IDS is small, and all of them are closed.
9. **All products are closed and priced privately.** No public per-ECU price was found. An open, permissively licensed, auditable sensor whose rules can be reviewed (for example during type-approval audits) is a positioning gap.
