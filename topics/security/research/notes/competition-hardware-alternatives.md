## 2. Where an IDS still adds value

- **Legacy fleets without SecOC.** No public SecOC adoption statistic exists. Toyota's own rollout began only in MY2021 [V, wtogami/docs]. The EU car fleet averages 12.7 years [V, ACEA 2026]. Most cars on the road therefore have unauthenticated classic CAN, and an IDS (incl. retrofit/aftermarket) is the only detective control there [I]. NXP also notes that "Existing ECU designs cannot be upgraded" when the µC lacks compute for SecOC [V].
- **Partial SecOC coverage and grace periods.** In practice SecOC is applied to "only a low fraction of the CAN messages", with truncated MAC/FV and "potential unsecured grace periods" after ignition or reboot [V, NXP/eeNews]. Profile 2 has no freshness value at all, so replay is not blocked [V, AUTOSAR PRS]. Unprotected IDs and windows still need monitoring [I].
- **Compromised authentic sender / extracted keys.** CIDS paper: "when an adversary has full access to any data stored in RAM and/or FLASH ... (e.g., shared secret keys), some cryptographic solutions become incapable" [V]. This happened in practice with the RAV4 Prime EPS key extraction [V, hardwear.io]. Secure transceivers also cannot stop a compromised ECU from sending its *own* permitted IDs with malicious content [I]. That leaves behavioural, timing and semantic anomaly detection as the remaining layer.
- **DoS, bus-off and error-frame attacks.** Cho & Shin state explicitly that MACs "cannot prevent the proposed bus-off attack" and that "prospective security-enhanced" networks remain vulnerable [V]. CIDS paper: preventive measures "alone cannot guarantee complete security due to their inability to handle certain critical attacks, e.g., Denial-of-Service" [V]. VoltageIDS was designed to tell bus-off attacks apart from errors [U]. Caveat: stealthy variants (CANnon, silent bit-flip bus-off, Janus/CANCloak) also evade classic message-level IDS [V]. Only error-frame-aware or physical-layer monitoring helps against them, and the authors partly call for hardware fixes [V].
- **Flooding from nodes without a secure transceiver.** The NXP leaky bucket only limits the local host [V]. An OBD aftermarket dongle or a non-NXP ECU is not rate-limited [I], so a network-wide IDS still sees it.
- **Aftermarket devices on OBD.** NXP itself names "an aftermarket device that is not part of car OEM remit" as the rogue sender that RX-side invalidation targets [V]. That only works for IDs whose owner carries a secure transceiver [I].
- **Detection and forensics for VSOC / UN R155.** R155 §7.3.7 requires measures "to detect and prevent cyber-attacks", support for the OEM's monitoring capability, and "data forensic capability to enable analysis of attempted or successful cyber-attacks" [V via globalautoregs summary of 7.3.7]. §7.2.2.2(g)/§7.2.2.4 require continual monitoring incl. analysis "from vehicle data and vehicle logs" [U]. Prevention-only mechanisms (SecOC, transceivers, CANsec) block traffic but produce no fleet telemetry by themselves. In AUTOSAR the IDS architecture (Security Sensors → IdsM → Security Event Memory / IdsR → SOC/SIEM) collects such events. BSW modules report standardized security events into it, so SecOC verification failures become IDS inputs [V for the architecture, AUTOSAR FO RS IDS R25-11; the SecOC-as-sensor example is [I], since the SecOC event list was not opened].
- **Sender attribution.** Fingerprinting IDS (CIDS, VoltageIDS, EASI) can identify *which* ECU sent an attack frame [V for CIDS and EASI]. Neither SecOC (shared symmetric keys) nor ID allow-lists provide this, and it is useful for VSOC triage [I].
- **Defense in depth is the vendors' own framing.** NXP positions the secure transceiver as complementing "crypto-based security solutions with an additional layer in a Defense-in-Depth (DiD) concept" [V]. The CIDS authors frame message authentication and intrusion detection as the "two main lines of defense" [V]. No AUTOSAR document was found that literally says "IDS complements SecOC"; that framing is implied by the IdsM architecture [I].
- **Timing and sequence anomalies.** Freshness counters only check ordering per PDU. An attacker with valid keys, or the legitimate ECU under compromise, can still send at wrong rates or in wrong sequences across PDUs, which is detectable by timing and sequence IDS [I]. Counter-evidence: CANnon and silent bus-off produce "no changes in timing" [V], so timing IDS have blind spots.
