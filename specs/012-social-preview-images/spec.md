# Feature Specification: Social preview images for every zoo page

**Feature Branch**: `012-social-preview-images`

**Created**: 2026-10-11

**Status**: Draft

**Input**: User description: "Every published model has its own page by now. We need logic that generates images fit for social media, so that a shared link shows a good image: always the model name, always the Mobility Model Zoo logo, and perhaps a very short one-liner on what the model does and what its USP is. It has to be generated by us. Think about how best to solve this, perhaps created automatically whenever a new model arrives."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A shared model link shows the model, not just the zoo (Priority: P1)

The owner posts the link to a model page (for example scout-large) on LinkedIn, Mastodon, Slack or in a messenger. The link preview shows an image made for that model: its name, the Mobility Model Zoo mark and wordmark, and a one-line statement of what the model does and why it is worth a look. Today every page shares the same generic zoo image, so a reader cannot tell from the preview which model is meant.

**Why this priority**: Sharing model links is how the zoo reaches its audience. A preview that names the model and its value is what makes someone click.

**Independent Test**: Build the site, open the preview metadata of the scout-large page in a link-preview checker (or a platform's post inspector), and see an image with "scout-large", the zoo mark and the model's one-liner.

**Acceptance Scenarios**:

1. **Given** a published model with its website text, **When** the site is built, **Then** the model page declares its own preview image, and that image shows the model name, the zoo mark and wordmark, and the model's one-liner.
2. **Given** the model page link is pasted into a platform that shows large link previews, **When** the preview renders, **Then** the image is shown in large format without cropping away the name, the mark or the one-liner.
3. **Given** a model whose latest release is non-commercial or experimental, **When** its preview image is generated, **Then** the image states this as clearly as the model page does, so the preview never promises more than the page.

---

### User Story 2 - A newly published model gets its image without anyone designing it (Priority: P1)

A model is published through the release pipeline. Its page appears on the website, and its preview image is created with it, in the same build, from the same registry data. Nobody draws, exports or uploads an image by hand, and nobody has to remember to.

**Why this priority**: The owner wants to approve releases, not produce assets. A manual step would be forgotten and leave new models with the generic or a stale image.

**Independent Test**: Add a second published model with website text to a test registry, build the site, and see that its page has its own preview image with no other change.

**Acceptance Scenarios**:

1. **Given** a model is published for the first time, **When** the site is rebuilt after the release, **Then** its page has its own preview image without any manual step.
2. **Given** the one-liner or the release status of a model changes, **When** the site is rebuilt, **Then** the image shows the new text or status, and platforms that cache previews are offered the new image rather than the old one.
3. **Given** a model's website text would not fit on the image, **When** the release gate or the site build runs, **Then** it stops with a message naming the model, the text and the limit, before anything is published.

---

### User Story 3 - The start page and other pages share well too (Priority: P2)

The owner shares the zoo's start page or an output format page. The start page shows a zoo image (mark, wordmark, the zoo's tagline). A format page shows its format name with the zoo mark. The current hand-made zoo image is replaced by one generated the same way, so changing the zoo tagline updates it.

**Why this priority**: Model pages matter most, but every shareable page should have a fitting image, and one generation path is easier to keep right than a hand-made image beside it.

**Independent Test**: Build the site, check that the start page and each format page declare an image that shows the right title, and that changing the zoo tagline changes the start page image on the next build.

**Acceptance Scenarios**:

1. **Given** the site is built, **When** the start page link is shared, **Then** the preview shows the zoo mark, wordmark and tagline.
2. **Given** an output format page, **When** its link is shared, **Then** the preview shows the format name and the zoo mark.
3. **Given** the 404 page, **When** it is shown, **Then** it uses the zoo image and is not offered as its own share target.

---

### User Story 4 - Images are checked like the rest of the site (Priority: P2)

Before the site is deployed, the same automated checks that guard the pages also check the images: right size and format, file size within platform limits, text fully visible, enough contrast, an alternative text, and no third-party resources. A failing image blocks the deploy, as a failing page does.

**Why this priority**: The owner does not review by hand. A broken or misleading preview would go out unnoticed otherwise.

**Independent Test**: Make a model's one-liner too long or give an image the wrong size in a test registry and see the site check fail with a message naming the page.

**Acceptance Scenarios**:

1. **Given** a built site, **When** the site check runs, **Then** every page that declares a preview image has one that exists, has the agreed size and format, and stays under the file size limit.
2. **Given** an image whose text was cut off or overflows its area, **When** the site check runs, **Then** the check fails and names the page.
3. **Given** a preview image, **When** the page's metadata is read, **Then** it carries an alternative text that says what the image shows.

---

### Edge Cases

- **Long model names**: a name that does not fit on one line at the normal size is set smaller or wrapped; if it still does not fit, the build fails rather than cut the name.
- **One-liner with numbers**: the image cannot carry the footnote that says what a number is measured against, so the one-liner on the image contains no free-standing numbers and no metric placeholders (digits inside names stay allowed); the build rejects one that does.
- **No one-liner given**: the model's tagline is used if it fits and contains no numbers; otherwise the build asks for a short line in the model's website text.
- **Deprecated model**: the image says "deprecated", as the page does.
- **Unpublished models**: they have no page, so they get no image; the start page image does not list them.
- **Sandbox models**: never get a page or an image.
- **Platform caching**: platforms keep a preview for days; a changed image gets a new address so the next share shows it.
- **Non-Latin or accented characters** in a name or one-liner render correctly with the self-hosted fonts, or the build fails instead of showing missing-glyph boxes.
- **Dark mode**: platforms show the image as it is; one image design must read well on both light and dark platform themes.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Every page of the website that can be shared (the start page, every published model page, every output format page) MUST declare its own preview image in the metadata that link-preview services read, for both the Open Graph and the large-image card convention.
- **FR-002**: A model page's image MUST show the model name, the Mobility Model Zoo mark and wordmark, and the model's one-liner. It SHOULD use the model's visual motif from the website, so models are told apart at a glance.
- **FR-003**: The image MUST show the release status as the latest release record states it: "experimental" for an experimental release, "deprecated" for a deprecated one, and "Non-commercial" for a model whose usage class is non-commercial. The model page MUST show the same labels at its top, so the image never says more than the page.
- **FR-004**: The one-liner MUST come from the model's website text, the same place as the rest of its page text. It MUST be at most 90 characters and MUST contain no free-standing numbers and no metric placeholders; digits that are part of a name (for example "M3 Pro" or "jtbd-span-v1") are allowed, as everywhere on the site. If no separate short line is given, the tagline is used when it meets these rules; otherwise the release gate and the build fail with a message that asks for a short line.
- **FR-005**: Images MUST be generated automatically from the registry by every site build. Publishing a model, changing its website text or its release status MUST be enough to update its image on the next build, with no manual design, export or upload step.
- **FR-006**: The release gate rule that checks a model's website text before publishing MUST also check the one-liner rules of FR-004, so a release never leads to a site build that fails on the image.
- **FR-007**: The generation MUST run inside the zoo's own build: no external image service, no third-party fonts or resources, no network access during generation. It MUST use the self-hosted fonts and the zoo mark.
- **FR-008**: Images MUST be 1200 × 630 pixels, in a format all major platforms accept, at most 1 MB each, with the important content inside the area that platforms crop to for square or smaller previews.
- **FR-009**: Each image MUST have an alternative text in the page metadata that names what it shows (for example "scout-large, Mobility Model Zoo: finds jobs, pains and gains in mobility texts").
- **FR-010**: When an image's content changes, its address MUST change too, so platforms that cache previews fetch the new image.
- **FR-011**: The site check MUST verify, for every page that declares an image: the file exists, has the size and format of FR-008, stays under the file size limit, its text was set without overflow or truncation, the text colours meet WCAG AA contrast against their background, and the alternative text is present. A failure MUST block the deploy.
- **FR-012**: The image's text MUST match the page: the model name and one-liner on the image MUST be the same strings that the page's metadata states, and the site check MUST compare them.
- **FR-013**: The generic, hand-made zoo image MUST be replaced by the generated start-page image; the manual script that produced it MUST be retired or turned into the generation path.
- **FR-014**: The same build from the same registry and code MUST produce the same images, byte for byte or by an equivalent comparison, so an unchanged model does not get a new image address.
- **FR-015**: The images MUST follow the zoo's identity (colours, type, mark) as defined for the website, and MUST NOT carry advertising, sponsor or third-party branding.
- **FR-016**: Adding a model or a topic MUST NOT require any change to the image generation; only the model's website text is needed.

### Key Entities

- **Preview image**: one image per shareable page; attributes: page, title text, one-liner, status labels, motif, alternative text, address that changes with its content.
- **Share line (one-liner)**: a short statement of what a model does and why it matters; part of the model's website text; at most 90 characters, no numbers; falls back to the tagline when that meets the rules.
- **Image template**: one layout per page type (zoo, model, format) that places mark, wordmark, title, one-liner, status labels and motif.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100 % of shareable pages in a build declare their own preview image, and 100 % of those images pass the site check.
- **SC-002**: A model published for the first time has its own preview image on the live site within the same deploy as its page, with zero manual steps.
- **SC-003**: In the post inspectors or preview tools of at least three platforms (for example LinkedIn, Mastodon and Slack), the shared link of a model page shows the large image with the model name, the zoo mark and the one-liner fully visible.
- **SC-004**: Three people from the target group who see only the link preview of a model page can say which model it is and, in their own words, what it does.
- **SC-005**: Generating all images adds at most one minute to a site build with five published models.
- **SC-006**: Rebuilding without any registry change produces the same image addresses for every page.

## Constitution Compliance

Principles this feature touches, and how it complies (constitution 2.1.0):

- **III. Measure before optimizing, metric naming**: the image carries no numbers, because it cannot carry the note that says what a number is measured against (FR-004).
- **VI. Clean provenance**: images use only the zoo's own mark, motifs and self-hosted OFL fonts; no source text or personal data appears on an image.
- **IX. Reproducible, dated releases; usage class**: images are generated from the registry by the build, never by hand; "Non-commercial", "experimental" and "deprecated" appear on the image as on the page (FR-003), so a preview never presents a restricted or experimental model as more than it is.
- **Project scope & layout**: a new model or topic needs no change to the generation (FR-016).
- **Tasks and releases**: the release gate's website-text rule covers the one-liner (FR-006), so the release pipeline stays the only path to a published page and its image.
- **Resources & cost**: generation runs in the existing free CI; no cash budget is needed.
- **Compliance (owner direction 2026-10-08)**: no third-party service or resource, no tracking, no branding or advertising (FR-007, FR-015).

Principles I, II, IV, V, VII, VIII and X are not touched: the feature does not extract, label, train, measure or compare models.

## Assumptions

- The images are generated during the site build, which already runs in CI after every change to the registry and after every release; this is what makes them automatic. Generating them once at release time and committing them to the repository was considered and rejected: it would add a manual or extra pipeline step and could go stale when the zoo identity changes.
- Hand-designed images per model (for example with Claude Design) are not used for the per-model images; the layout per page type is designed once in the zoo identity and then filled from data. A design refresh of the template is a separate, optional step.
- 1200 × 630 pixels is the size that LinkedIn, Facebook, Mastodon, Slack, X, Bluesky and messengers use for large link previews; other sizes (square, story formats) are out of scope.
- The images live on the website only. Hugging Face model cards and the Hugging Face organisation card keep their own previews; changing those is out of scope.
- Images are not posted to any platform by this feature; sharing stays a manual act of the owner.
- Today only scout-large is published; the feature is tested with a second, fixture model so that the automatic path for new models is covered before the next real release.
